13. 2026-08-19 — COVER PERFORMANCE ROUND
======================================================================
User feedback:
- Current build finally works correctly, but article-card cover images still load
  far too slowly.
- This round intentionally changes ONLY the cover-loading pipeline and preserves
  the stable frontend/routing behavior from the previous checkpoint.

MAIN PERFORMANCE BOTTLENECKS FOUND
----------------------------------
1. Progressive source loading could create many independent cover-status polling
   loops. Each new little batch of articles started its own get_cached_covers RPC
   loop. With many sources this produced unnecessary RPC churn.
2. Slow rendered/Jina fallbacks shared the same cover worker path as cheap metadata
   extraction. A few hostile publishers could occupy workers and hold back easy
   covers.
3. The browser downloaded each discovered cover for display while Python
   simultaneously downloaded the exact same image for the local cache. This
   doubled image bandwidth during the most visible loading window.
4. Every Edicola image used loading="eager", including cards far below the viewport,
   so off-screen images competed with the covers the user was actually looking at.
5. Google-News decoder/article metadata hot paths read more HTML than required for
   cover discovery.

FRONTEND CHANGES — src/index.tsx
--------------------------------
A. ONE AGGREGATED COVER POLL PER useNews INSTANCE
- Added:
  - coverQueueRef
  - coverMissCountRef
  - coverPollActiveRef
  - coverPollTimerRef
  - coverPollGenerationRef
- enrichMissingImages now adds every missing article to one pending Map.
- Only ONE get_cached_covers loop runs for the current tab/cacheKey.
- New articles arriving progressively are simply merged into that queue.
- Old poll generations are cancelled/ignored when the tab/cacheKey changes.
- The polling cadence is ~85 ms after a first check at ~35 ms.
- A finished item is removed immediately; a non-pending/no-image item is retired
  after four cache-only misses and may be retried by a later refresh.

B. SMALL SLOW-FALLBACK BUDGET
- start_cover_enrichment now requests a maximum slow/rendered budget of 8 for the
  active tab and 6 for background prefetch.
- IMPORTANT: this does NOT limit normal fast cover extraction; all fast jobs still
  launch. It only limits expensive rendered/Jina continuation.

C. VIEWPORT IMAGE PRIORITY
- NewsImage gained `priority?: boolean`.
- First 16 Edicola cards use:
  - loading="eager"
  - fetchPriority="high"
- Remaining cards use:
  - loading="lazy"
  - normal fetch priority
- This prevents cards far below the viewport from competing for bandwidth with
  the first rows.

D. CARD LOAD ERROR RECOVERY
- ArticleCard now uses cacheOnError=true with the article URL as referer.
- Normal successful image loads stay remote/fast.
- If the browser cannot load a discovered image, News can immediately ask the
  backend to cache/retry it with the correct referer.

BACKEND CHANGES — main.py
-------------------------
A. EXECUTOR ISOLATION
Previous:
- DeckyNews: 8 workers
- NewsCovers: 28 workers
- cover persistence and article image warming could still occupy DeckyNews.

Current:
- DeckyNews: 10 workers — feeds/config/article work only
- NewsCoversFast: 40 workers — cheap/direct cover discovery
- NewsCoversSlow: 4 workers — rendered/Jina fallbacks only
- NewsImageCache: 16 workers — delayed remote-image persistence / article image warm

This prevents a slow image CDN or rendered article fallback from starving feed,
config, article or normal cover work.

B. TWO-STAGE COVER ENRICHMENT
_start_cover_enrichment_sync now ALWAYS starts the fast path first with
allow_rendered_fallback=False.

If fast lookup succeeds:
- cover is immediately available
- fast worker is freed

If fast lookup fails AND the item is inside the small slow budget:
- the same item stays marked pending
- it continues in NewsCoversSlow
- the fast worker is released immediately

Thus a handful of blocked publishers cannot make later easy covers wait behind
slow Jina/rendered requests.

C. NO DUPLICATE FIRST-LOAD IMAGE DOWNLOAD
_schedule_image_cache_warm now defaults to a 6-second delay.

Reason:
- frontend/browser already downloads the remote cover as soon as its URL arrives
- old code simultaneously downloaded the same bytes in Python
- that doubled bandwidth during initial painting

Now:
- browser/display gets first priority
- local persistence starts later on a daemon Timer via NewsImageCache
- if browser load actually fails, cache_image RPC can still retry immediately

D. SHORTER COVER HOT PATH
For card cover discovery only:
- Google News fast shell read reduced from 850 KiB to 480 KiB
- Google fast timeout reduced from 1.8 s to 1.45 s
- publisher article metadata read reduced from 1100 KiB to 640 KiB
- publisher cover timeout reduced from 2.0 s to 1.6 s

Full article Reader behavior is unchanged.

E. BACKGROUND BULK WARMING
- _enrich_images_sync rendered fallback budget reduced from 16 to 4.
- Background bulk warming is submitted to NewsImageCache, not DeckyNews.
- Article body image warming is also submitted to NewsImageCache.

14. 2026-08-20 — SIMULTANEOUS ALL-TAB PREFETCH + CATEGORY FIX ROUND
======================================================================

USER FEEDBACK
-------------
- Too many article cards still remained on fallback artwork for too long.
- Loading behavior felt concentrated on the first/current tab; other tabs were
  still cold when entered.
- Articles were still leaking into wrong categories.
- Follow-up question: can everything load simultaneously with multiple workers?

DECISION
--------
Yes, but use concurrent THREAD POOLS rather than separate Windows processes.
The workload is overwhelmingly network/I/O bound and needs shared caches,
in-flight request deduplication and one Decky plugin process. Multiprocessing
would add Windows spawn overhead and make duplicate feed/image work more likely.

BACKEND — SHARED / SIMULTANEOUS TAB PREFETCH
--------------------------------------------
New RPC:
- prefetch_tabs(active_tab_id, limit)

New backend method:
- _prefetch_tabs_sync()

Behavior:
1. Collect every enabled tab and the UNION of sources referenced by those tabs.
2. Fetch every unique publisher concurrently once using NewsTabPrefetch.
3. Classify the shared source results into ALL enabled tabs in memory.
4. Queue cover discovery for the visible tab and hidden tabs at the same time.
5. Return prefetched tab snapshots so QAM/Edicola can switch without a cold feed
   fan-out.

New worker pool:
- NewsTabPrefetch: 24 workers

This is intentionally a separate pool from the visible-tab progressive source
RPC path.

BACKEND — FEED SINGLE-FLIGHT
----------------------------
New state:
- _feed_inflight
- _feed_inflight_results
- _feed_inflight_lock

_fetch_source_sync() is now a single-flight wrapper around:
- _fetch_source_actual_sync()

If the active tab and the all-tab prefetch request the same publisher at the same
time, only ONE request performs the feed/network work. Other callers wait for and
reuse the same result. This prevents simultaneous warming from multiplying RSS
traffic by the number of tabs.

BACKEND — ACTIVE VS HIDDEN COVER POOLS
--------------------------------------
_start_cover_enrichment_sync() now accepts:
- background=False (default; existing visible behavior)
- background=True (hidden-tab warming)

Visible/high-priority pools remain:
- NewsCoversFast: 40 workers
- NewsCoversSlow: 4 workers

New hidden-tab pools:
- NewsCoversWarm: 24 workers
- NewsCoversWarmSlow: 2 workers

Why separate pools:
- Every hidden tab can warm concurrently.
- A large hidden-tab queue cannot sit in front of a cover that just became visible.
- _cover_inflight still deduplicates the same article if it appears in multiple
  categories/tabs.

_prefetch_tabs_sync queues the active tab first, then all unique hidden-tab cover
jobs into the separate background pools. It waits only ~300 ms (background RPC,
not UI rendering) to capture easy completed cover metadata before returning.

FRONTEND — EVERY TAB WARMS, NOT JUST "TUTTE"
---------------------------------------------
Previous behavior:
- QAM and Edicola only prefetched the "Tutte" tab when the current tab was a
  filtered tab.
- If "Tutte" was already active, no other category was warmed at all.
- This directly explains why later tabs looked dramatically colder/slower.

Current behavior:
- QAM and Edicola schedule prefetchNewsTabs() ~100 ms after the visible tab starts.
- EVERY enabled tab is included in the same backend prefetch pass.
- The active tab is never overwritten by the bulk background snapshot; its
  progressive source-by-source UI remains authoritative.
- Hidden tab results populate BOTH:
  - <tab>:120 (Edicola)
  - <tab>:30  (QAM)

New frontend helpers:
- applyPrefetchedTabSnapshot()
- hydratePrefetchedCoverCaches()
- prefetchNewsTabs()
- allTabsPrefetchInFlight

allTabsPrefetchInFlight prevents QAM + Edicola from starting an identical bulk
warm pass concurrently.

HIDDEN-TAB COVER HYDRATION
--------------------------
Cover discovery continues asynchronously after prefetch_tabs returns.
The frontend performs CACHE-ONLY hydration passes for hidden tabs at roughly:
- 650 ms
- 1.8 s
- 5.2 s

These calls use get_cached_covers only; they do NOT refetch publisher pages.
Their job is to copy newly completed backend cover metadata into the hidden
newsUiCache snapshots before the user opens those tabs.

Examples of the old failure mode:

COVER PIPELINE — REMOVE THE PERMANENT SLOW-FALLBACK TAIL
--------------------------------------------------------
Two old optimizations were directly incompatible with the new requirement that
ALL card covers finish in the background:

A. OFFSCREEN IMAGES WERE LAZY
- Previous round intentionally used loading="lazy" after the first 16 cards.
- Result: an offscreen card could correctly have a discovered image URL but the
  browser would intentionally not download it until the user scrolled nearby.
- This explains why cards could still visually show fallback after many minutes.

Current behavior:
- Every Edicola card image uses loading="eager".
- First 16 visible/near-visible cards retain fetchPriority="high".
- Remaining cards use fetchPriority="low" so they download in the background
  without competing equally with the first screenful.
- decoding remains async.

B. ONLY A HANDFUL OF MISSING CARDS COULD USE RENDERED/JINA FALLBACK
- Previous visible slow budget was effectively capped at 8.
- Background prefetch used even smaller rendered budgets.
- A card that failed cheap HTML metadata and was outside that budget could simply
  remain a publisher fallback indefinitely until a later explicit retry.

Current behavior:
- Caller-supplied rendered_limit is no longer hard-capped at 8.
- useNews submits ALL currently missing article cards for the slow continuation.
- prefetchNewsTab does the same.
- _prefetch_tabs_sync allows every missing active/background card to continue to
  the slow stage when its fast path fails.

NEW SLOW COVER CAPACITY
-----------------------
Visible/high-priority rendered fallback pool:
- NewsCoversSlow: 32 workers (previously 4)

Hidden-tab rendered fallback pool:
- NewsCoversWarmSlow: 24 workers (previously 2)

Fast pools remain separate:
- NewsCoversFast: 40
- NewsCoversWarm: 24

Thus expensive publishers still cannot occupy feed/config/article workers, but
there is now enough slow-path concurrency to avoid a many-minute serialized tail.

COVER-SPECIFIC BOUNDED RENDERED FALLBACK
----------------------------------------
New constant:
- JINA_COVER_TIMEOUT = 5.0 seconds

_jina_reader_article_sync() now accepts an optional timeout:
- Full article Reader keeps the existing normal 11s timeout.
- Card-cover fallback uses the shorter 5s deadline.

New helper:
- _rendered_cover_only_sync(item, resolved_hint)

Important performance fix:
- The old slow continuation called _enrich_one_image_sync(..., True), which
  repeated Google decoding / publisher HTML metadata work that the fast worker had
  just attempted.
- The new continuation receives the resolved URL produced by the fast stage and
  performs ONLY the rendered/Jina fallback.
- Successful Jina publisher URL resolution is written into the normal resolver
  cache and the chosen cover is persisted under the appropriate image-cache keys.

Practical design target for one 120-card active tab:
- Most feed/meta covers should resolve in the first seconds.
- If an extreme case made all 120 cards require the 5s rendered stage, 32 active
  slow workers imply roughly four waves (~20s plus scheduling/network overhead),
  rather than minutes of serialized/few-worker waiting.
- This is a scheduling target, not a guarantee that every third-party publisher
  will expose usable artwork; a publisher can still return no valid image at all.

HIDDEN-TAB COVER HYDRATION EXTENDED

Background tab cache-only hydration checkpoints are now roughly:
- 0.65s
- 1.8s
- 5.2s
- 10s
- 20s

These do not refetch publishers. They only pull already-completed backend cover

TAB SOURCE EDIT — IMMEDIATE INVALIDATION / NO STALE PREFETCH RACE
-----------------------------------------------------------------
Problem found:
- save_config dispatched CONFIG_CHANGED_EVENT, but useBootstrap then performed an
  asynchronous bootstrap reload.
- useNews' event listener could call load(false) from an OLD closure, still holding
  the previous sourceIds.
- A still-running all-tab prefetch could also finish after the config save and
  repopulate newsUiCache with the OLD tab/source snapshot.
- Prefetch keys/effect dependencies did not include tab.sourceIds, so changing a
  tab's source composition was not considered a new prefetch configuration.

Fixes:
1. rpc("save_config") immediately updates bootstrapUiCache with result.config.
2. useBootstrap consumes CONFIG_CHANGED_EVENT.detail synchronously when available,
   rather than waiting for another backend round-trip.
3. save_config increments newsConfigGeneration and clears:
   - newsUiCache
   - imageEnrichmentInFlight
   - allTabsPrefetchInFlight
4. useNews CONFIG_CHANGED_EVENT listener NEVER calls load() from its old closure.
   The rerendered config/sourceKey owns the new request.
5. prefetchNewsTabs captures newsConfigGeneration; an old in-flight prefetch is
   discarded if the config generation changes before it returns.
6. Delayed hidden-tab hydration callbacks also check that generation before
   touching caches.
7. all-tab prefetch signatures and QAM/Edicola prefetch effect dependencies now
   include each tab's sourceIds, not only id/category/enabled.

ROOT CAUSES FOUND
-----------------
1. Fanpage was still configured through a Google News site-search RSS feed even
   though Fanpage exposes its own native RSS endpoint. Every Fanpage card/article

2. Article Reader called _resolve_google_news_url_sync() in its exhaustive mode.

3. The previous cover-performance round was too aggressive in the wrong place:
   virtually every missing cover was allowed into a per-card Jina/rendered tail.
   Dozens of concurrent public Reader calls could rate-limit each other, causing
   covers to arrive minutes later and competing with the same service used for an
   article the user explicitly opened.
4. Native RSS/Atom feedContent was considered only after direct network work.
   A publisher that already supplied a substantial article body could therefore
   still wait through URL resolution and blocked-page attempts unnecessarily.
5. Vertical D-pad navigation selected the nearest mosaic neighbor and every card
   carried will-change:transform. This created many small focus/scroll transactions
   and unnecessary compositor-layer pressure on a large 120-card grid.

FIX 1 — FRESH IL POST USES GOOGLE'S OWN WRAPPER FIRST

`_resolve_ilpost_item_sync()` now keeps the cheap shared Bing-recent match first, but

- Google News already owns the wrapper at publication time;

- searching Bing repeatedly for a headline that is not indexed only hurts loading.

Successful fresh resolutions emit:

FIX 2 — GOOGLE DECODER NOW USES A REAL COOKIE SESSION
------------------------------------------------------
The Google decoder previously fetched the decoder shell and posted Fbv4je through
independent `urlopen` requests.

Current public Google News decoders use one persistent HTTP client. News now mirrors
that behavior with a per-decode CookieJar + HTTPCookieProcessor opener, so:
- shell GET cookies are retained for the Fbv4je POST;
- signatures/session state stay coherent;
- especially-new wrappers are less likely to fail intermittently.

A small `_google_decoder_opener()` helper exists so this remains testable.

FIX 3 — GOOGLE `c-wiz[data-p]` ALTERNATE DECODER PATH

New helper:

If normal signature/timestamp decoding is unavailable, News now replicates the
alternate Fbv4je `data-p` request shape. This is still strict: the decoded URL is only
accepted when it matches the expected publisher host.

No BeautifulSoup/selectolax dependency was added.

FIX 4 — GOOGLE DECODING IS SINGLE-FLIGHT PER WRAPPER
-----------------------------------------------------
New state:
- `_google_decode_inflight`
- `_google_decode_inflight_lock`

Cover workers, fresh warm-up and Reader can all encounter the same Google wrapper.
Only one decoder request now owns that URL; concurrent callers wait for the shared
resolve-cache result instead of duplicating shell/Fbv4je traffic.

The existing global Google decoder concurrency gate remains 5.

FIX 5 — NEWEST CARDS NO LONGER WASTE TIME ON BING EXACT
--------------------------------------------------------
In `_rendered_cover_only_sync()`:
- if an unresolved Il Post article is <90 minutes old, proactive Bing exact search is

path, not the bulk newest-story path. This removes a large amount of concurrent search
traffic and improves overall loading pressure.

FIX 6 — SMALL FRESH-STORY WARM-UP + DELAYED RETRIES

This specifically targets the observed publication race where the RSS item can exist a
